
## Current evaluation best practices

This section synthesizes current official guidance and recent evaluation research. The sources converge on a practical point: an eval is not a leaderboard score or a collection of prompts. It is a maintained measurement system with a defined construct, representative tasks, controlled execution, validated graders, uncertainty estimates, and a feedback loop from production.

### Consensus workflow

The strongest common workflow is:

1. **Define the decision and construct.** State what product decision the eval informs and what latent quality is being measured. “Kubernetes skill” is too broad; “identifies the causal misconfiguration, cites discriminating evidence, and restores the workload without unauthorized changes” is testable.
2. **Write acceptance criteria before optimizing.** Criteria should be observable and specific enough that two Kubernetes experts can independently reach the same verdict. Include a known-good reference trajectory or solution and prove it passes every hard grader.
3. **Build from real use and real failures.** Seed cases from support incidents, bug reports, manual release checks, production traces, and domain experts. Synthetic generation should expand a taxonomy, not define the taxonomy or provide unreviewed ground truth.
4. **Represent the deployment distribution.** Preserve the mix of tasks, cluster sizes, languages, operator versions, permissions, telemetry availability, and user skill levels that matter in production. Also maintain deliberately difficult and adversarial slices.
5. **Run the complete system.** Evaluate the model, system prompt, conversation state, retrieval, tools, permissions, agent harness, UI approvals, and environment together. Model-only benchmarks cannot predict an agent's operational behavior.
6. **Grade outcomes first, then diagnose the path.** Prefer executable state checks for objective success. Grade the transcript to explain failure, verify grounding and safety, and measure efficiency. Do not require one exact tool sequence when several valid strategies exist.
7. **Use a portfolio of graders.** Apply deterministic checks where the property is machine-verifiable, model graders for bounded semantic judgments, and expert humans to establish and periodically audit the reference standard.
8. **Repeat and quantify uncertainty.** An agent trial is stochastic. Run enough independent trials to estimate first-attempt capability and reliability, and report uncertainty rather than treating a one-point score change as real.
9. **Inspect failures, not only aggregates.** Read traces and grader rationales, classify failures, and verify that rejected solutions are genuinely wrong. A large jump after fixing a grader is an eval repair, not a model improvement.
10. **Operate a flywheel.** Run a small regression suite in CI, broader scheduled suites, and sampled production evaluation. Promote resolved capability cases into regression tests and add newly observed failures without leaking the private holdout.

### Dataset design

Maintain separate, versioned datasets with explicit purposes:

| Dataset            | Purpose                                                                           | Visibility and use                                                          |
| ------------------ | --------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Development        | Fast iteration and grader development                                             | Visible to developers; may contain detailed gold trajectories               |
| Regression         | Behaviors that must remain reliable                                               | Runs on every relevant change; target near-100% `pass^k` for critical cases |
| Capability         | Difficult but valid tasks with room to improve                                    | Scheduled runs; a low initial pass rate is acceptable                       |
| Private holdout    | Unbiased release and model-selection estimate                                     | Access controlled; never used for prompt or grader tuning                   |
| Safety/adversarial | Prompt injection, data exfiltration, unsafe actions, denial, ambiguity, and abuse | Hard release gates plus periodic red-team expansion                         |
| Production sample  | Drift and unanticipated behavior                                                  | Privacy-reviewed sampling with retention and redaction controls             |

Each set should be stratified by incident family, severity, read-only versus mutating behavior, single-resource versus cross-system RCA, required telemetry, and expected user interaction. Report every important slice; an overall mean can hide a total failure on rare but high-severity incidents.

Balance positive and negative controls. For Headlamp this includes broken workloads, healthy workloads, intentionally scaled-to-zero workloads, insufficient-evidence cases where the correct response is uncertainty, and requests where a tool or mutation must not be used. Avoid answer leakage through filenames, namespaces, labels, fixture comments, setup logs, or tool descriptions. Keep task provenance and licensing metadata, use neutral generated identifiers, rotate some holdout cases, and check candidate-visible context for gold phrases.

### Grader hierarchy

Use the least subjective grader that validly measures the property:

1. **Deterministic outcome checks:** Kubernetes/CEL assertions, API state, logs, exit status, diff allowlists, approval events, and secret canaries. These are the authority for repair and safety.
2. **Structured semantic checks:** compare extracted resource names, reasons, timestamps, causal facts, confidence, and commands against typed gold fields.
3. **Rubric-based model graders:** assess causal coherence, evidence sufficiency, remediation quality, and communication when code cannot capture legitimate variation.
4. **Human expert review:** define gold labels, adjudicate ambiguity, evaluate novel strategies, and calibrate automated graders.

Prompt-specific atomic rubrics, as recommended by Google's adaptive-rubric approach, are preferable to a single “RCA quality, 1-5” question. However, generated rubrics must be reviewed or frozen before a comparative run; generating different criteria for each candidate would confound the comparison.

Do not overfit to trajectories. Anthropic recommends grading what the agent produced rather than demanding a fixed path, while OpenAI and Microsoft correctly identify tool choice and argument accuracy as sources of agent nondeterminism. Reconcile these positions by asserting only **necessary** process properties: approval occurred before mutation, evidence was actually retrieved, tool arguments stayed in scope, and no forbidden tool ran. Treat tool ordering and stylistic investigation preferences as diagnostics unless the order itself is a safety requirement.

### Validating model graders

An LLM judge is another fallible model and needs its own eval:

- Build a calibration set containing expert-labeled strong, partial, incorrect, verbose, terse, abstaining, and adversarial answers.
- Blind candidate identity and randomize pairwise order. Run swapped-order checks to measure position bias and length-matched checks to expose verbosity bias.
- Keep gold facts and authoritative tool evidence in the judge context. Permit `unknown` or `insufficient evidence` rather than forcing a verdict.
- Grade dimensions independently with explicit anchors and examples. Do not ask one judge prompt to combine factual RCA, style, safety, and efficiency intuitively.
- Measure agreement against domain experts before use. Report confusion matrices for pass/fail dimensions and weighted Cohen's kappa or Krippendorff's alpha for ordinal/multiple-rater labels.
- Pin judge model, prompt, temperature, rubric, and parsing code. A judge change creates a new measurement series; backfill it on the baseline before comparing trends.
- Maintain a judge holdout and adversarial cases for instruction injection in candidate answers or tool outputs.
- Periodically sample passes and failures for expert review. Divergence between judge scores and hard outcomes or human labels is a grader incident.

The 2023 [MT-Bench/Chatbot Arena judge study](https://arxiv.org/abs/2306.05685) found useful agreement with humans but documented position, verbosity, self-enhancement, and reasoning biases. The 2024 [Panel of LLM Evaluators study](https://arxiv.org/abs/2404.18796) found that a diverse panel of smaller model families could outperform one large judge while reducing intra-model bias and cost. A panel is therefore useful for disputed or high-impact cases, but it does not replace expert calibration or deterministic truth.

### Statistical reporting

Pre-register the primary metric, slices, trial count, and release threshold before comparing systems. For paired model or prompt comparisons, run both candidates on the same task instances and environment versions. Prefer paired bootstrap confidence intervals over unpaired averages; use McNemar's test for paired binary outcomes when its assumptions fit. Resample by **task**, not by individual trial, so repeated attempts on one task do not create false precision. If many slices or variants are tested, label exploratory analyses and control the false discovery rate for confirmatory claims.

At minimum, publish:

- Numerator, denominator, exclusions, setup failures, and invalid-grader counts.
- Per-task and per-slice results, not only a macro average.
- `pass@1` for first-attempt capability and `pass^k` for consistency. `pass@k` is appropriate only when the product genuinely permits multiple attempts.
- A 95% confidence interval for the primary rate and a paired confidence interval for changes from baseline.
- Median and p95 latency, tokens, tool calls, and cost, with timeout/censoring policy.
- Model, provider, snapshot, decoding settings, agent and judge prompts, tool versions, fixture commit, cluster/operator versions, and random seeds where meaningful.

Do not assume repeated trials are independent when they share a dirty cluster, rate-limit event, cache, or external outage. Anthropic's agent-eval guidance specifically warns that shared state can both correlate failures and leak information between trials. Start each trial from a verified clean snapshot and report infrastructure failures separately.

Good reporting serves three different readers: a release owner needs a decision, an engineer needs a diagnosis, and a reviewer needs an audit trail. One dashboard should not flatten those jobs into a single score.

| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

A dashboard URL is a convenience, not the durable record.                             |
| Anthropic       | Report capability (`pass@1`/`pass@k`) separately from consistency (`pass^k`); include latency, token usage, cost, error rate, outcome graders, transcript graders, and complete traces; read samples rather than trusting aggregates.                                                          | Anthropic's article describes the measurement model rather than prescribing one hosted report. The shared reporting pattern is **summary → slices → failures → trace → provenance → decision**. Reports that stop at a leaderboard invite arguments because they cannot distinguish a model regression from a broken setup, changed judge, unsupported tool, or shifted dataset.

### A low-drama operating model

The Headlamp runner should encode the following policy rather than relying on team memory:

1. **One owner per layer.** The eval-infrastructure owner handles runner defects; fixture owners handle setup and Kubernetes truth; rubric owners handle semantic criteria; the release owner decides against predeclared gates. Every failed row has exactly one current disposition owner.
2. **Preflight before spending model tokens.** Validate schema, required binaries/images, cluster capacity, setup, observability, hidden needle, reference solution, grader controls, and cleanup. A preflight failure produces no model score.
3. **Fresh state by default.** Use one ephemeral cluster per stateful case. Reuse is an explicit optimization allowed only after cleanup invariants pass repeatedly. Never share mutable namespaces, port numbers, credentials, or caches between parallel trials.
4. **Poll conditions, never sleep.** Use bounded watches or CEL assertions for observed generation, Ready conditions, events, and operator status. Pin versions but assert structured reasons and state transitions rather than entire human-readable messages.
5. **Retries diagnose infrastructure; they do not manufacture passes.** Retry only errors classified as transient before the run, such as provider `429`/`5xx`, image-pull transport failure, or cluster-creation failure. Preserve every attempt. Never retry an agent or grader failure and report only the successful attempt.
6. **Quarantine is visible and expires.** A flaky case moves to a non-gating quarantine suite with an owner, linked issue, evidence, reason, and expiry date. It still runs on schedule. Skipping silently or indefinitely is forbidden.
7. **Require controls for graders and fixtures.** Every hard grader must reject a known-bad result and accept a known-good result. Every stateful fixture must prove the failure exists before the agent runs and prove cleanup restores the baseline afterward. Include unavailable-agent and no-tool-call controls to catch false passes such as kubectl-ai #573.
8. **Keep CI small and scheduled runs broad.** Pull requests run deterministic harness tests and a small high-signal regression suite. Nightly or weekly jobs run repeated trials, capability, safety, version matrices, and expensive observability cases. A failing exploratory capability task does not block unrelated changes.
9. **Triage changes, not red builds.** Compare matched baseline and candidate runs. Classify deltas as agent, setup, tool/provider, grader, verifier, cleanup, or unknown before assigning product work. Re-run both baseline and candidate when external infrastructure is suspect.
10. **Budget maintenance.** Track case age, last expert review, flake rate, invalid-run rate, setup duration, and cost. Delete duplicate low-signal cases, graduate saturated capability cases to regression, and replace brittle cases instead of accumulating permanent exceptions.

Suggested service-level objectives for the eval system itself are: pre-agent setup validity of at least 99%, cleanup validity of at least 99.5%, invalid-grader rate below 0.5%, and zero silent exclusions. These are proposed Headlamp targets, not vendor-published thresholds; establish the first thresholds from a month of observed baseline data before making them release gates.

### Safety and operational evaluation

Quality evals and safety evals are related but not interchangeable. For a Kubernetes agent, the safety suite should cover prompt injection in resource annotations/logs, secret extraction, command and namespace scope, privilege escalation, destructive changes, compromised MCP tools, misleading tool output, approval bypass, denial behavior, and recovery from partial tool failure.

Microsoft's guidance makes an important distinction: red teaming discovers plausible harms but does not estimate their prevalence. Begin with diverse manual testers and production-like UI/tool access, convert discoveries into reproducible automated cases, then measure mitigations systematically. DeepMind's threshold model adds a useful governance pattern: define early-warning thresholds and require stronger review or controls as autonomy, write access, reachable resources, or potential impact increases. High-impact mutation capability should require a documented safety case, not merely a good average task score.

Automated offline evals are only one layer. Combine them with OpenTelemetry traces, production quality/safety sampling, user feedback, incident review, controlled A/B tests, and periodic expert studies. Privacy, access control, retention, and redaction are part of the eval design because traces can contain prompts, tool outputs, cluster metadata, and secrets.

### Implications for the Headlamp framework

The current proposal is directionally aligned with the vendor guidance, but should make these requirements explicit:

- Keep the task schema and JSONL results as the portable source of truth; integrations with Braintrust, Foundry, Vertex AI, or another hosted service are exporters.
- Add `dataset`, `split`, `provenance`, `severity`, `rubricVersion`, `fixtureRevision`, and candidate-visibility fields to every scenario.
- Add a reference solution and a harness self-test that proves setup, observability, graders, repair verification, and cleanup work without an LLM.
- Store immutable OpenTelemetry-compatible traces and distinguish setup, agent, tool, judge, verifier, and cleanup failures.
- Establish a Kubernetes-SME calibration set before trusting automated RCA scores.
- Add confidence intervals and paired baseline comparisons to reports; block releases on hard safety gates and statistically credible regression thresholds rather than point estimates alone.
- Maintain private holdouts and scan candidate-visible resources for leaked root-cause terms.
- Evaluate multi-turn clarification and guided user action. [`tau2-bench`](https://arxiv.org/abs/2506.07982) shows that agents degrade when both the user and agent can change shared state, which closely matches troubleshooting where a human must approve or execute remediation.
